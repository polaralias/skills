# Coordination runtime adapter

Use only when isolated parallel, integration-branch, or stacked Git delivery is justified. Store one manifest outside removable worktree containers and run `rke coordination validate --manifest <path>` before allocation. The validator checks the explicit base, sibling-container paths, unique branches and worktrees, non-overlapping single-writer paths, and acyclic dependencies. Shared-path integration owners, inherited authority, validation classes, and stack usefulness still require deliberate review; the validator does not prove them. `coordination plan` returns argv arrays only; it never creates worktrees or grants push, merge, deploy, or publication authority.

For a plan-only request, inspect the manifest and current base, run `coordination validate` and `coordination plan`, then report the resulting argv, ownership, dependency order, sibling locations, and unresolved integration checks promptly. Do not allocate worktrees or conduct implementation review merely to present a non-mutating plan.

Before allocation, inspect existing managed worktrees and each candidate checkout's status, branch and uncommitted work. Reuse a suitable owned checkout where possible. Refresh and identify the authoritative base before making a new lane; the main checkout's clean status says nothing about another worktree. Choose independent sibling lanes for disjoint changes, an integration branch when the combined tree needs a named owner, or a stack only when an upper change depends on a lower one. Assign one integration owner for shared files, renames and generated artifacts. Record dependency order and which checks can run independently; run checks that share mutable resources serially.

Require worker handoffs to identify actual commits, changed ownership paths, validation results and remaining risks. Integrate in dependency order and validate the resulting combined tree, including interactions absent from worker tests. After rewriting a lower stack layer, rebase affected upper layers and repeat invalidated reviews and checks. Do not treat an old passing receipt as evidence for the new commits.

Distinguish ancestry proof, a provider's exact reviewed-head integration proof, and a recorded rewrite chain. They answer different questions. The current automated cleanup supports ancestry proof only. Provider evidence or a rewrite record may justify an integration assessment but cannot make a rewritten source tip eligible for automated removal. Preserve that branch and worktree and report the unsupported cleanup case; never substitute a same-name PR or force deletion for the required proof.

Reconcile current Git and provider state before relying on recorded evidence. Targeted worker success never replaces integrated-tree validation. Merge, publication, deployment, and cleanup remain separate. Cleanup requires a clean worktree, exact current source tip, durable integration evidence, absent remote branch, and preservation of dirty, advanced, rewritten, or unintegrated work. A cascading rebase invalidates affected upper-layer receipts.

Use `rke coordination cleanup-check --lane <name> --branch <source-branch> --review-head <exact-reviewed-commit> --remote <remote-name> --destination-branch <name>` immediately before considering cleanup. The read-only check requires the lane's owned sibling worktree, a clean tree, current source tip identical to the reviewed commit, an observed destination tip on the named remote containing that exact source commit, and absence of the source branch on that remote. Fetch the destination commit first if it is not present locally. A merged same-name PR, stale review receipt, local-only merge or unreachable remote does not qualify. The check never removes a worktree or branch; an eligible result is evidence for a separately authorised cleanup action, not permission to delete other paths.

Only when current user authorization covers cleanup of this exact lane and branch, run `rke coordination cleanup` with the same reviewed head, remote and destination. It reruns the eligibility checks immediately before removal, then uses Git to remove only the owned clean sibling worktree and its local branch. It never deletes the remote branch. If worktree removal succeeds but local branch deletion fails, report the partial state; do not force-delete or retry against a different tip. Reconcile current provider PR state separately: local ancestry does not prove which PR was merged.
